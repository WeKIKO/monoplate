# Development guide

## Add a domain, route, and schema

The generators refuse to overwrite existing files. The following example creates a `catalog` bounded context and a list endpoint:

```sh
pnpm generate:domain -- --name catalog --entity Product --description "Product catalog"
pnpm generate:route -- --domain catalog --name list-products --method get --path /api/v1/products
pnpm db:generate
pnpm api:client:generate
pnpm check
```

The domain generator creates the entity, repository port, use case and unit test under `domains/catalog`; its shared DTO under `packages/contracts`; a Drizzle table under `packages/database/src/schema`; and API adapter wiring under `apps/api/src/modules`. The route generator adds a Zod contract, OpenAPI route, application operation and tests.

Review generated names and business rules before treating the scaffold as production code. Replace the generated in-memory repository with a Drizzle adapter in the API composition root when persistence is required. Never use `pnpm db:push` for production releases: generate, review and commit a migration instead.

## Contract and migration workflow

After changing an HTTP contract, run `pnpm api:client:generate` and commit both `apps/api/openapi.json` and `packages/contracts/src/generated/api.ts`. CI detects drift with `pnpm api:contract:check`.

After changing a Drizzle schema, run `pnpm db:generate`, inspect the SQL and snapshot in `packages/database/migrations`, then exercise it against a disposable database. Destructive SQL requires an explicit `-- monoplate:allow-destructive <reason>` annotation and additional review.

## Generated versus editable files

| Path | Ownership |
|---|---|
| `packages/design-tokens/tokens.json` | Editable source of truth |
| `packages/design-tokens/generated/*` | Generated by `pnpm tokens:generate`; do not hand-edit |
| `apps/api/openapi.json` | Generated by `pnpm api:openapi:generate`; commit it |
| `packages/contracts/src/generated/api.ts` | Generated by `pnpm api:client:generate`; do not hand-edit |
| `packages/database/migrations/*.sql` and `meta/*` | Generated, then reviewed and committed; do not silently rewrite applied migrations |
| `.monoplate/project.json` | Initializer-owned project identity; commit it and edit only through an explicit migration |
| Domain/application/adapter scaffolds | Generator-created starting points; editable after creation |

Generated files retain their provenance through their directory/name and the command documented above. A change is complete only when its matching `--check` command passes without rewriting the worktree.
